## 摘要（只看这 10 条）

1. **工程质量是可信的**：10 个 smoke 套件全绿（可解析出 ≥276 条断言），分层、守卫、质量门禁、工作区隔离、密钥脱敏都是真实实现，不是文档摆设。
2. **最大的 token 浪费不是"调用太多"，而是"单次返回太大"**：一次 `pipeline_status` 在真实 6 任务运行上是 **19.7K 字符**（naive ≈4.9K tok，CJK 感知 ≈7.1K tok），其中 **71% 是 `agents[]` 重复回传的 L2 完整 prompt**（`storeToBoard` 直接 `{...a}`）。→ O1
3. **第二处**：`pipeline_checkpoint` 把整份交接文档（真实项目 18.5K 字符）通过 `content` 原样回传，再加 `coldStartPrompt`：≈4.6K / 6.4K tok 一次。→ O2
4. **第三处是结构性的**：L3 生成的代码在 `execute_local`/`execute_batch`/`spawn_local_executor` 结果里回传一次（≈1K tok/子任务），L2 还必须把它原样写进磁盘文件（再付 ≈1K tok 输出）——**同一份代码付两次**；而质量门禁核对的是"板子上的字符串"，不是磁盘文件。→ O6 / B7
5. **每请求固定开销 ≈2.7K tok**（协议 436 + 19 个工具 schema 2,234），但它位于可缓存的稳定前缀上，实际计费影响通常远小于 2.7K。**不要为此做大重构**，瘦身 10–20% 即可。→ O4 / O5
6. **预算守卫看不到 L2 的真实消耗**：`maxTotalTokensPerRun` 只累加 spawn/send 的 prompt 估算（`l1.js:327,393`），L2 每轮的大头没进账；板上 `estimatedTokens` 反而是 tokenMeter 的真实测量值——两个数不一致。→ O7 / B14
7. **三处契约与实现不一致**：L1 的 "bounded takeover" 无法通过工具完成（`register_output`/`review` 被守卫限定 L2/L3）；`pipeline_decompose` 让每个子任务继承**模块级**验收（`l2l3.js:108`），与 SKILL"每个子任务自己的验收"矛盾；SKILL 说 L3 执行器"write complete code"，但**插件没有任何代码落盘**。→ B4 / B5 / B7
8. **一个安全问题**：`wsPath()` 不限制在工作区内（`l2l3.js:13`），`register_output` / `review(filePath)` / `register(filePath)` 可读任意文件；读进来的内容会被存成 `code`，并在 review 时交给 gate 的子进程执行。→ B3
9. **L1 上下文比率被低估**：只统计最近 40 条事件、且不含固定前缀（`dsh-compat.js:89-97`）；本会话实测 `9,104 / 64,000（14%）`，而真实输入明显大于这个数——"该交接时没交接"的风险真实存在。→ B10
10. **修复优先级**：先 B3/B4/B7（安全与正确性），再 O1/O2/O6（token），最后 O3/O4/O5/O7 与打磨项。全部为局部改动，`npm test` 可覆盖大半。

## 三、可优化项（按"token 收益 / 改动成本"排序）

### O1（P0，最大单项）`pipeline_status` 瘦身：20K → ≈4K 字符，省 ≈4–6K tok/次

现状（`plugin/lib/tools/l1.js:223-246`）：直接回传 `board.tasks` / `board.subtasks` / `board.agents`，而 `storeToBoard`（`store.js:273`）对 agent 做 `{...a}`，把 L2 的 `desc`（就是 spawn 时的完整 prompt，实测单个 2.1–3.3K 字符）原样带回。

修复建议（`board-route.js` 的 `buildBoardSnapshot()` 已有正确投影，可直接复用/抽取）：
- `agents`: 只留 `{id,label,state,model,scopeDir,estimatedTokens,tokens}`；
- `tasks`/`subtasks`: `{id,parent,state,assignee,desc:desc.slice(0,60),acceptance:acceptance.slice(0,80),codeLines,failCount}`；
- 新增 `verbose:true` 参数，需要全文时才展开；
- `recentMessages` 同时修 B1（见下）。
预期：19.7K → ≈4K 字符；对 20 任务项目，单次可省 ≈15–20K tok。

### O2（P0）`pipeline_checkpoint` 不再回传正文，省 ≈4.6–6.4K tok/次

`l1.js:526` 返回 `{path, content: text, coldStartPrompt}`。正文已经写盘，模型刚生成过，回传是纯重复。
改为 `{path, bytes, lines, sections:9, coldStartPrompt}`；需要正文时让模型 `read` 该文件（仍是一次读，但不会"每次 checkpoint 都付"）。

### O3（P1）`pipeline_plan` 少回显，省 ≈0.7–1K tok/次

`pipeline_plan` 返回每个 task 的完整 `desc`+`acceptance`（模型刚提交的内容）。改为 `tasks:[{id,assignee,depends_on,state}]` + `milestones` + `planHint`，加 `verbose` 兜底。
注意：plan 是低频调用，收益中等；但它同时是"最容易让上下文膨胀"的一步（大项目 20 任务时 ≈6K 字符）。

### O4（P1）协议段瘦身：436 → ≈180 tok/请求

`prompts.js:9` 的 10 行里，工具名枚举、里程碑规则、预算规则与 SKILL 有重复。保留 5 行核心（分层/禁轮询/验收门/预算/知识入口），删去可与 SKILL 重复的细节。省 ≈250 tok × 每次请求（缓存前缀，实际收益打折）。

### O5（P2）工具面瘦身 + L2 工具白名单

- 合并 `pipeline_scan` / `pipeline_ledger` / `pipeline_recall` 为一个 `pipeline_knowledge(op)`，省 2 个 schema；
- 压缩 `pipeline_spawn_module_lead` 的 9 个参数描述（现 252 tok，最大单条）；
- **关键**：L2 只用到 6 个 L2/L3 工具 + 文件工具，却和 L1 共用同一份工具表。若 DSH 的 `agentOptions` 支持工具白名单，给 L2 传入即可省 ≈1.6K tok/轮（L2 轮数通常最多，这一项可能比 O4 更值）。需先确认宿主 API。

### O6（P1，结构性收益最大）让插件负责"代码落盘"，而不是把代码回传给 L2 再写一遍

现状：`execute_local` 返回 `code`（`l2l3.js:318`）、`spawn_local_executor` 返回 `code`（`l2l3.js:605`）；插件不写任何交付文件（`l2l3.js` 中无 `writeFileSync`），L2 必须自己把代码复制进文件。

建议 API：
```
pipeline_execute_local({ subtaskId, filePath })  // filePath 相对 scopeDir
  → { ok, path, lines, sha8, gate:{ok,score}, state }
```
- 插件写文件（`ensureDir` + `writeFileSync`），门禁直接读这个文件；
- 省掉"回传 + 重写"两次计费（≈2K tok/子任务）；
- 同时让门禁的真相源变成磁盘文件（解决 B7），并让 `register_output` 的语义统一为"登记已有文件"。
- 兼容：保留 `returnCode:true` 或 `verbose` 供调试。

### O7（P1）把 L2 的真实消耗接进预算

`maxTotalTokensPerRun` 目前只统计 spawn/send 的 prompt 估算。建议每次 `send_to_lead` / `drain_leads` 时，把 `tokenMeter` 测到的 `surfaceTokens` 增量（`board-route.js` 的 `measureAgentTokens` 已有实现）累加进 `counters.tokensIn/Out` 与 `addRunUsage`。
否则 500K 的预算上限对"6 个 L2 各跑 20 轮"这种真实成本几乎不可能触发，预算守卫形同虚设。

### O8（P2）`mode=off` 仍注册 19 个工具

激活门限选择 `normal`/`off` 后，守卫会拒绝执行，但 schema 仍随每次请求发送。若在意，可在 `activation.choice !== 'enable'` 时只注册 3 个入口工具（lock/status/knowledge）；代价是切换回 enable 需要重开会话。

### O9（P2）SKILL 全文 2,764 tok

按需加载、一次会话一次，**不建议大幅压缩**（它是能力主体）。若要省，把 Phase 3 的调度细节移到 `docs/`，正文压到 ≈2,200 tok，省 ≈500 tok/会话。

### O10（P2，非 token）`board.json` 每次 `record()` 同步写 + 全量 agents

`store.js:221-243`：每个事件都把 `storeToBoard`（含 agent 完整 prompt）以 2 空格缩进写盘。真实 6 任务运行 = 33KB/次；20 任务 + 10 个 L2 可能 100KB+/次。
修复：`snapshotBoard` 用 O1 的投影 + 紧凑 JSON（`JSON.stringify(x)` 不带缩进），可减 ≈70% IO 与磁盘占用。

## 四、Bug 与正确性

### B1（P0）`recentMessages` 的 160 字符截断完全失效
`l1.js:242-246` 用 `m.text` 判断长度，但 `store.js:229-240` 的 `record()` 写的是 `task_desc`/`task_conclusion`/`acceptance_criteria`，**没有 `text` 字段**。结果：每个消息对象原样返回（含完整 task_desc/acceptance）。
实测印证：本会话 `pipeline_status` 返回 `recentMessages: []`（store 恢复后 messages 为空，见 B11），代码路径上的截断同样不生效。
修复：`const t = m.text ?? m.task_conclusion ?? m.task_desc ?? ''`，并整体 `slice(0,160)`。

### B2（P1）配置校验键名拼写错误
`config.js:288` 的 `POSITIVE_KEYS` 含 `'maxLevel3OutputTokens'`，真实键是 `level3MaxOutputTokens`。后果：`/pipe-config level3MaxOutputTokens 0` 不会被拒绝，`max_tokens:0` 会让 L3 永远返回空。
修复：改键名，并补一条单测。

### B3（P0，安全）`wsPath()` 无工作区限制 → 任意文件读 + 门禁执行
`l2l3.js:13`：
```js
function wsPath(r, p) { return resolve((r?.store?.workspaceRoot) || process.cwd(), p) }
```
`resolve()` 遇到绝对路径或 `..` 会逃出工作区。使用点：
- `pipeline_register_output({filePath})`：`readFileSync(wsPath(...))`（`l2l3.js:634-635`）→ 可把 `~/.ssh/id_rsa` 之类读进 `subtask.code`，持久化进 `board.json`/`trace`；
- `pipeline_review({filePath})`（`l2l3.js:433-437`、`465-467`）→ 读入后交给 `gates.js` 的 node/python 子进程执行。
L2 是 agent，需求文本可被注入，这条链路等价于"任意文件读取 + 任意代码执行"。
修复：与 `recall.js` 同一规则——拒绝绝对路径、`..` 逃逸，`resolve` 后必须 `startsWith(workspaceRoot + sep)`；或只允许 `scopeDir` 内相对路径。

### B4（P0）子任务继承模块级验收，与文档矛盾
`l2l3.js:108`：`acceptance: task.acceptance`。每个被 decompose 出来的子任务都拿**模块**的验收标准；而 SKILL.md:64-65 要求"L2 writes each subtask's own"。
后果：`gateSubtask` 用模块级断言去判定单个子任务代码 → 误判（该过的不过、该拦的拦不住），"每子任务可机械验证"的设计落空。
修复（二选一）：
1. decompose 让 LLM 输出 `[{desc, acceptance}]`，缺省才回退 `desc`；
2. 显式要求 decompose 参数带 `acceptances:[]`（与 desc 等长）。
建议同时把 `gateTask` 的模块级验收与子任务级验收分层记录，避免重复计分。

### B5（P1）L1 "bounded takeover" 在工具层不可能完成
SKILL.md:143-145 写"L1 直接写代码，然后 register through the gate"，但 `guards.js` 把 `review`/`register_output` 列为 `L2L3_TOOLS`，L1 调用会被 `strictAdjacencyDenial` 拒绝。
修复：给 `register_output`/`review` 增加"L1 takeover 例外"（仅在 `run.counters.l1Takeovers>0` 或显式 flag 下），或把 SKILL 改成"L1 接管时只写文件、不进门禁，由用户验收"。
两种都能自洽，**但必须二选一**，现在的状态是文档承诺了做不到的事。

### B6（P2）`footerR` 共享可变变量存在跨工作区竞态
`plugin.js:137,161,165`：`let footerR = null` 在模块作用域，每次工具调用赋值，`withRunFooter(..., () => footerR)` 读的是最后一次赋值。两个 L1 会话（不同工作区）并发调用时，A 的返回可能带上 B 的流水线状态。
修复：把 run 引用放进每次调用的闭包（`withRunFooter(registered, register => () => entry.r)`），不要用模块级变量。

### B7（P0，能力问题）门禁核对字符串，不核对磁盘文件
`gates.js` 的 `gateSubtask`/`gateTask` 默认用 `subtask.code`（板子上的字符串）执行断言；插件自身不落盘。结果：一个模块可以 `state=done` 而磁盘上什么都没有（L2 忘了写、或写错文件）。`filePath` 参数存在但是可选的、默认不用。
修复：与 O6 合并——执行即落盘，门禁读文件；在 `done` 之前强制校验文件存在且 hash 与门禁内容一致。

### B8（P2）`maxLevel3Retries` 的回退默认值不一致
`l2l3.js:256,283` 用 `2`，`l2l3.js:444` 用 `5`，配置默认是 `5`。正常合并配置后不触发，但"配置缺键"路径行为不同。
修复：统一 `numCfg(cfg,'maxLevel3Retries',5)`。

### B9（P1）`estimateTokens` 对中文低估 ≈30%
`util.js:35`：`Math.ceil(JSON.stringify(input).length / 4)`。实测同一份真实 payload：naive 4,935 tok，CJK 感知 7,091 tok（差 44%）。
影响：L3 输入预算判断、L1 上下文比率、trace 里缺 usage 时的 token 记账全部偏低。
修复：中文按 ≈1.6 字符/token 估算（`cjk/1.6 + other/4`），或直接对字符串而非 JSON 序列化计字符。

### B10（P1）L1 上下文只数最近 40 条事件
`dsh-compat.js:89-97`：`TAIL_EVENTS=40`，且只累加 `estimateMessage` 到消息类事件。
影响：会话越长越低估；本会话实测 `9,104/64,000（14%）`，而固定前缀 + 早期内容都不在里面 → 交接提醒可能来得太晚，直到 DSH 自己压缩。
修复：优先用 `tokenMeter` 的会话累计值（若有）；否则按"事件总数 × 平均"做外推，并在 40 条窗口上乘一个随会话增长的系数；至少在读数旁标注"近似值"。

### B11（P2）恢复会话丢消息
store 的 `restore` 只加载 `run.json`/`board.json`/`requirement_lock.json`，不恢复 `messages`。重启后 `pipeline_status.recentMessages` 为空（本会话已实测为空），footer 的事件依据也变弱。
修复：`messages` 从 trace 尾部回放最近 20 条（trace 本来就有），或在 board.json 里带上最近 10 条。

### B12（P2）decompose 的 LLM 截断静默降级
`decomposeViaLlm` 的 `maxTokens:1000`，解析失败时静默走 `splitIntoChunks`，调用方只看到 `via` 字段，没有提示"LLM 分解失败"。
修复：返回 `decomposeFallback:true` + 原因，让 L2 决定是否重试。

### B13（P2）`package.json` 未声明 DSH 版本约束
插件依赖 v84+ 的 subagent API（`startActivation`），但 `engines`/`dsh.engines` 为空。旧宿主上安装会在运行时报错，错误信息对用户不可读。
修复：在 `package.json` 里加 `engines: { dsh: ">=…" }`（或 `dsh.engines.dsh`），与 README 的支持版本一致。

### B14（P1，语义）`totalTokens` 与看板 `measured` 不是一回事
`l1.js:219` 的 `totalTokens` 来自 `counters`（只含 L3 与 spawn/send 估算），看板的 `estimatedTokens`/`tokens` 来自 tokenMeter 实测。同名不同义，用户会误判成本。
修复：同 O7，把两边统一为"实测优先、估算兜底"，并在字段名上区分 `trackedTokens` / `measuredTokens`。

### B15（P2）selftest 的 `ok:false` 会被误读为"插件坏了"
`pipeline_selftest` 在无本地 L3 引擎时返回 `ok:false, degraded:['L3 engine']`（本机实测），其余 4 项均为 ok。模型/用户容易直接判定不可用。
修复：输出改成 `ok:true, degraded:[...]` 或顶层区分 `ready/degraded`。

## 五、安全

| 项 | 风险 | 建议 |
|---|---|---|
| B3 路径穿越 | **高**：任意文件读 + 门禁执行 | 收敛到 workspace/scopeDir（P0） |
| 门禁执行用户代码 | 中：子进程 + 黑名单 + AST guard，但**不是沙箱** | 保持 `allowCodeExecution` 默认开的同时，文档加粗"仅本地开发"；CI/共享机默认关 |
| `/pipeline/board` 无鉴权 | 低：localhost；但 `?workspace=` 能按需加载任意带项目标记的目录并回传 requirement/tasks | 多用户机器上加一次性 token；或只允许已知 workspace |
| `pipeline_scan root` 任意绝对路径 | 低：L1 工具，secret 文件按名排除，但 index 会暴露目录结构 | 限制在项目根或明确提示 |
| L2 prompt 注入放大 B3 | 中：L2 可被需求文本诱导读敏感文件 | 修 B3 后自然收敛 |

## 六、能力评估（对照"提升复杂项目开发能力"）

**做得好的**
- 三层分工明确，L1 只做协调与决策，L2 长活复用、L3 一次性代码，符合成本模型。
- DAG + 上游失败阻塞 + 里程碑硬门禁（`done-unaccepted` 阻止 spawn/send）+ 用户确认验收，流程闭环。
- 知识层是机械生成（scan 0 模型 token），`index.md` 只有 4.5K 字符（≈1.1K tok），比让模型读仓库便宜一个数量级；`recall` 有路径收敛与脱敏。
- 守卫 fail-closed（未知 tier 拒绝执行）、密钥脱敏、footer 状态回显，细节到位。
- 前端看板投影很克制（desc 120 / requirement 200 / events 6×90 / agents 只留 L2）——**UI 侧已经做对的事，工具侧没做**（O1 的对照证明改动可行）。

**会拖后腿的**
- B7 让"质量门禁"的真相源是字符串而不是文件——最终交付质量取决于 L2 是否老实落盘。
- B4 让逐子任务验收失真，门禁分数不可信。
- B10 + B9 让"上下文甜点区"这个卖点读数偏低，交接时机偏晚。
- O7/B14 让预算守卫对最大成本项（L2 轮次）失明。
- 本机无 L3 引擎（selftest 实测）时，"必须走 L3"的硬规则与"自动降级"并存，会产生无谓重试；建议在 Phase 2 适配评估里把 `level3Endpoint` 为空直接判为"降级模式：所有代码任务由 L2 直写"，并让协议文本据此切换。

**不建议做的**
- 不要为了省 2.2K 的工具 schema 去做大重构（缓存前缀，实际单价低）。
- 不要删 footer（每次 ≈40 字符，换来的是"模型始终知道里程碑状态"）。
- 不要把 SKILL 压得太狠——它是能力主体，2.7K tok 一次会话很划算。
